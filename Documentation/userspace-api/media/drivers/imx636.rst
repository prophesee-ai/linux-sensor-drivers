Sony IMX636 sensor driver
=========================

Introduction
------------

The Sony IMX636 sensor is an Event-Based Vision Sensor (EVS) designed in
cooperation between Sony and Prophesee. An EVS detects movement with high
temporal resolution by detecting luminance changes, which each pixel senses
asynchronously, and only outputting the differential data after combining with
the coordinate and time information.

Output format control
---------------------

Output format selection in Prophesee Evt 2.1 and 3.0 formats are supported,
however, in evt 2.1, the two halves of the 64-bit event are inverted, resulting
in a kind of middle-endianness, advertised as ``PSEE_EVT21ME``.

Provided that ``media-ctl`` from `v4l-utils <https://linuxtv.org/wiki/index.php/V4l-utils>`_
has been built with the above media codes in its sources, it can be used to
configure the IMX636 output format as follow:

.. code-block:: none

	media-ctl -V "'imx636 6-003c':0[fmt:PSEE_EVT21/8192x196]"

If either ``PSEE_EVT21`` or ``PSEE_EVT21ME`` is requested, the format is set to
``PSEE_EVT21ME``, otherwise, ``PSEE_EVT3`` is set.

The width and height given to media-ctl are the size and number of packets per
frame on the bus, and are unrelated to the geometry of the sensor.
The user-space can use the selection API to get the bounds of the encoded
events.

The packetization on the MIPI CSI-2 link is independent from the pixel array
size, and the frame rate in the CSI-2 protocol is arbitrary. Those are kept to
their default value, and are not affected by output format selection.

Region of Interest (crop)
-------------------------

It is possible to deactivate rows and columns on the pixel matrix, disabling a
pixel when either or both its row and column are disabled. This allow to create
various selections on the pixel matrix. In this driver, only a rectangular
selection is implemented, using the ROI Window block to simplify register
accesses.

This selection is presented to userland through the V4L2 selection API, as crop,
and can be enabled via media-ctl:

.. code-block:: none

	media-ctl -V "'imx636 6-003c':0[crop(320,120)/640x480]"

The selection is done directly on the analog pixels, before serialization of the
events, effectively reducing the activity on the readout -the block that
serializes and timestamps the events-, but does not alter the coordinates of the
pixels. With the above selection, events may be generated between pixel(320,120)
and pixel(959,599).
Since cropping has no impact on the data packetization, it is allowed to update
it while streaming.

Test Patterns
-------------

The driver implement the standard test_pattern control menu (0x009f0903). The
following patterns are proposed:

Pixel Array
'''''''''''

Actually not a test pattern, this is the standard source of data of the sensor,
used in regular streaming.

Time base
'''''''''

Pixel events are represented by the polarity of the event (more or less light),
the coordinate of the pixel (x,y), and the time of the event, to preserve the
time accuracy while streaming the data over a packetized link, such as
MIPI CSI-2, or simply a DMA transfer before software processing.

The complete timestamp is not repeated in each event, the most significant bits
are updated through a dedicated event in the protocol, to save bandwidth. This
pseudo-pattern just keeps pixels in reset so that only timebase update events
(referred as time-high) are issued by the readout.

Selecting this pattern just alters the start-up sequence to keep pixels in
reset, but other settings may inject extra events in the stream, such as the
timestamping of external events ("external trigger"), or statistics computed
by the Event-Rate Controller, that are enabled by default.

Readout Pattern
'''''''''''''''

With this pattern, the read-out replaces the pixel-generated events by a fixed
pattern of events, each line producing for each group of 32 pixels an event of
positive brightness change with 0x5a5a5a5a as vector of triggered pixels,
followed by the same event with negative polarity.

The temporality of this pattern is changed by the output settings of the
sensor (number of lanes, frequency, inter-packet delays), thus the position of
the time-high events in the stream, as well as the streaming statistics, are
not easy to predict, making the pattern not ideal for bit-accurate verification,
but the presence and the non-repetition of pixel events can be checked, and the
pattern follows the event protocol which makes it displayable.

End Of Frame marker
-------------------

IMX636 outputs data at a variable rate, but performs framing at a fixed rate
(2ms per frame by default). This means a variable amount of data in each
frame, however, this is unusual for video sensors, and some receivers use a
DMA that does not report the actual size of its transfers. For such case,
IMX636 is able to insert one or two arbitrary 32-bit words before closing
the CSI-2 frame, allowing software to stop the evaluation of a buffer when
it sees this marker.

This feature is exposed as two user controls.

enable_end_of_frame_marker (0x00982900)
'''''''''''''''''''''''''''''''''''''''

This is a menu allowing to insert 32 ou 64 bits, with the option to replace
some bits in the first word to match the timebase as it would be inserted
in EVT2.0 or 2.1 formats.

end_of_frame_marker (0x00982901)
''''''''''''''''''''''''''''''''

This is a u32 array control, with 1 dimension of size 2. This allows to set
the two words that may be inserted by the sensor. If 64 bits are to be
inserted, the two u32 will be inserted at the end of the frame in the same
order as the control, and, within each word, bytes will be re-arranged as
the actual events data to match the endianness of the system running the
driver.

By default, both markers are set to 0xE019E019 (but are disabled). This
value is a valid monitoring event in each data format, that is not used for
other purposes.
